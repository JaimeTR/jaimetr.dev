## 1. Introducción contextual  

En los últimos años la web ha pasado de ser una colección de documentos estáticos a una plataforma de aplicaciones interactivas que compiten con software nativo. Según el **State of JavaScript 2023**, el 78 % de los desarrolladores elige React como su librería de UI principal, y el **tiempo medio de carga (TTFB) de los sitios que usan React** se sitúa en 2,7 s, apenas por encima del umbral recomendado por Google (2,5 s) para una buena experiencia de usuario.  

Sin embargo, la popularidad de React también ha expuesto una limitación estructural: **el árbol de componentes se vuelve cada vez más profundo y denso**, y cada actualización de estado puede desencadenar renders innecesarios que impactan directamente en los Core Web Vitals (Largest Contentful Paint, First Input Delay, Cumulative Layout Shift). En entornos empresariales donde los usuarios esperan respuestas en menos de 100 ms, una mala gestión del rendimiento se traduce en pérdida de conversiones, aumento del churn y, en última instancia, en mayores costos de infraestructura.  

Históricamente, la optimización en la web se centraba en la capa de red (CDN, HTTP/2) y en la entrega de recursos estáticos (minificación, tree‑shaking). Con la llegada de SPA (Single Page Applications) y la adopción masiva de React, el **cuello de botella ha migrado al cliente**: la CPU del navegador, la gestión del estado y la estrategia de renderizado son ahora los factores críticos.  

Resolver este problema hoy es imperativo porque:  

1. **Competencia en tiempo real:** los usuarios cambian de pestaña si la UI se siente lenta.  
2. **SEO técnico:** Google penaliza los LCP > 2.5 s, y los bots de rastreo ejecutan JavaScript antes de indexar.  
3. **Costos operacionales:** cada milisegundo extra de CPU se traduce en mayor consumo de energía en dispositivos móviles, lo que afecta la percepción de la marca.  

En este artículo, como mentor técnico, desglosaremos los fundamentos de la performance en React, mostraremos implementaciones reales con evolución de código, analizaremos casos de negocio y ofreceremos una hoja de ruta práctica para que cualquier equipo pueda elevar sus métricas sin sacrificar mantenibilidad.

## 2. Fundamentos y arquitectura  

### 2.1 Renderizado en React: reconciliación y diffs  

React mantiene un **Virtual DOM** que representa el estado UI en memoria. Cada vez que se llama a `setState` o se actualiza un hook, React ejecuta el algoritmo de **reconciliación** para comparar el árbol anterior con el nuevo y generar un **diff**. Solo los nodos que cambian se actualizan en el DOM real.  

**Trade‑off:**  
| Ventaja | Desventaja |
|---|---|
| Reducción de manipulaciones directas del DOM (costosas). | Cada render produce una nueva representación del árbol, lo que implica consumo de memoria y CPU. |
| Abstracción que simplifica la lógica de UI. | Si el árbol es grande y se renderiza sin control, el algoritmo de diff puede ser O(N) en cada actualización. |

### 2.2 Principios de arquitectura para performance  

1. **Componentes “puros”** – Un componente que siempre devuelve el mismo JSX para los mismos props es candidato a memoization.  
2. **Separación de responsabilidades** – Mantener la lógica de negocio (hooks, services) fuera de la UI evita renders innecesarios.  
3. **Lazy loading y code splitting** – Dividir el bundle en chunks que se cargan bajo demanda disminuye el **First Contentful Paint (FCP)**.  
4. **Virtualización de listas** – Renderizar solo los elementos visibles en pantalla (p. ej. `react‑window`).  
5. **Cache de datos** – Utilizar SWR, React Query o el nuevo `use` de React 18 para evitar fetches redundantes.  

### 2.3 Diagrama conceptual (descrito en texto)  

Imagina una arquitectura de tres capas:  

- **Capa de datos** (API REST/GraphQL, Supabase).  
- **Capa de lógica** (hooks personalizados, context, servicios).  
- **Capa de presentación** (componentes React).  

Los datos fluyen desde la capa de datos → lógica → presentación. Cada capa está aislada mediante interfaces TypeScript y los componentes de presentación son **funciones puras** que reciben datos a través de props. Cuando un hook de datos actualiza su cache, solo los componentes que consumen esa porción de estado se re‑renderizan, gracias a la combinación de `React.memo`, `useCallback` y `useMemo`.

## 3. Implementación práctica  

A continuación, presentaremos cinco ejemplos reales que evolucionan de una solución *naïve* a una versión *optimizada*. Cada bloque supera las 15 líneas y está listo para copiarse a un proyecto Next.js/React con TypeScript.

### 3.1 Ejemplo 1 – Renderizado de lista simple vs. virtualizada  

#### 3.1.1 Versión básica (lista completa)  

```tsx
// src/components/CustomerListBasic.tsx
import React, { useEffect, useState } from "react";
import axios from "axios";

/**
 * Renderiza una tabla con 10.000 clientes.
 * Cada fila se vuelve a renderizar al cambiar cualquier estado del padre.
 */
export const CustomerListBasic: React.FC = () => {
  const [customers, setCustomers] = useState<Array<{ id: number; name: string }>>([]);
  const [filter, setFilter] = useState("");

  // Carga inicial de datos
  useEffect(() => {
    const fetchCustomers = async () => {
      try {
        const { data } = await axios.get("/api/customers");
        setCustomers(data);
      } catch (err) {
        console.error("Error al obtener clientes:", err);
      }
    };
    fetchCustomers();
  }, []);

  // Filtrado simple en memoria
  const filtered = customers.filter((c) => c.name.toLowerCase().includes(filter.toLowerCase()));

  return (
    <div>
      <input
        placeholder="Buscar cliente"
        value={filter}
        onChange={(e) => setFilter(e.target.value)}
        className="p-2 border rounded"
      />
      <table className="w-full mt-4 border-collapse">
        <thead>
          <tr className="bg-gray-100">
            <th className="p-2 text-left">ID</th>
            <th className="p-2 text-left">Nombre</th>
          </tr>
        </thead>
        <tbody>
          {filtered.map((c) => (
            <tr key={c.id} className="border-t">
              <td className="p-2">{c.id}</td>
              <td className="p-2">{c.name}</td>
            </tr>
          ))}
        </tbody>
      </table>
    </div>
  );
};
```

*Problema:* Cada cambio de `filter` fuerza el re‑render de **10 000** filas, lo que supera los 60 fps y penaliza LCP.

#### 3.1.2 Versión optimizada con `react-window`  

```tsx
// src/components/CustomerListVirtualized.tsx
import React, { useEffect, useState, useMemo, ChangeEvent } from "react";
import axios from "axios";
import { FixedSizeList as List, ListChildComponentProps } from "react-window";

/**
 * Lista virtualizada: solo renderiza las filas visibles (≈10 en pantalla).
 * Utiliza memoization para evitar cálculos innecesarios.
 */
export const CustomerListVirtualized: React.FC = () => {
  const [customers, setCustomers] = useState<Array<{ id: number; name: string }>>([]);
  const [filter, setFilter] = useState("");

  useEffect(() => {
    const fetch = async () => {
      try {
        const { data } = await axios.get("/api/customers");
        setCustomers(data);
      } catch (e) {
        console.error("fetch error:", e);
      }
    };
    fetch();
  }, []);

  // Memoizamos el resultado del filtrado; se recalcula solo cuando customers o filter cambian
  const filtered = useMemo(
    () => customers.filter((c) => c.name.toLowerCase().includes(filter.toLowerCase())),
    [customers, filter]
  );

  // Renderizador de cada fila para react-window
  const Row = ({ index, style }: ListChildComponentProps) => {
    const customer = filtered[index];
    return (
      <div style={style} className="flex border-b p-2">
        <div className="w-1/4">{customer.id}</div>
        <div className="w-3/4">{customer.name}</div>
      </div>
    );
  };

  const handleFilter = (e: ChangeEvent<HTMLInputElement>) => setFilter(e.target.value);

  return (
    <div className="p-4">
      <input
        placeholder="Buscar cliente"
        value={filter}
        onChange={handleFilter}
        className="p-2 border rounded w-full"
      />
      {/* Altura fija de 500 px, cada fila 35 px */}
      <List height={500} itemCount={filtered.length} itemSize={35} width="100%" className="mt-4">
        {Row}
      </List>
    </div>
  );
};
```

**Mejoras:**  
- **O(N)** del filtrado sigue presente, pero el renderizado del DOM pasa a **O(V)** donde *V* es el número de filas visibles.  
- `useMemo` evita recomputar el filtro en renders que no cambian `filter` ni `customers`.  
- `react-window` mantiene el bundle bajo (< 30 KB gzipped).

### 3.2 Ejemplo 2 – Prop drilling vs. Context + memo  

#### 3.2.1 Versión básica con prop drilling  

```tsx
// src/pages/DashboardBasic.tsx
import React, { useState } from "react";
import { Header } from "../components/HeaderBasic";
import { StatsPanel } from "../components/StatsPanelBasic";

export const DashboardBasic: React.FC = () => {
  const [theme, setTheme] = useState<"light" | "dark">("light");

  const toggle = () => setTheme((prev) => (prev === "light" ? "dark" : "light"));

  return (
    <div className={theme === "light" ? "bg-white text-black" : "bg-gray-800 text-white"}>
      <Header theme={theme} onToggle={toggle} />
      <main className="p-4">
        <StatsPanel theme={theme} />
      </main>
    </div>
  );
};
```

```tsx
// src/components/HeaderBasic.tsx
import React from "react";

interface Props {
  theme: "light" | "dark";
  onToggle: () => void;
}

export const Header: React.FC<Props> = ({ theme, onToggle }) => (
  <header className="p-4 flex justify-between items-center">
    <h1 className="text-xl">Panel</h1>
    <button onClick={onToggle} className="p-2 rounded bg-indigo-600 text-white">
      Cambiar a {theme === "light" ? "oscuro" : "claro"}
    </button>
  </header>
);
```

```tsx
// src/components/StatsPanelBasic.tsx
import React from "react";

interface Props {
  theme: "light" | "dark";
}

/**
 * Cada vez que cambia el tema, este componente se vuelve a renderizar,
 * aunque sus datos internos (estadísticas) no cambien.
 */
export const StatsPanel: React.FC<Props> = ({ theme }) => {
  console.log("Render StatsPanel");
  return (
    <section className={theme === "light" ? "bg-gray-100" : "bg-gray-700"} p-4>
      <h2 className="text-lg mb-2">Estadísticas</h2>
      {/* Simulación de datos estáticos */}
      <div className="grid grid-cols-2 gap-4">
        <div className="p-2 bg-white rounded shadow">Visitas: 12 345</div>
        <div className="p-2 bg-white rounded shadow">Ventas: 678</div>
      </div>
    </section>
  );
};
```

**Problema:** Cada toggle de tema causa re‑render de `StatsPanel`, aunque su contenido no depende de `theme`. En aplicaciones con cientos de paneles, el coste se vuelve significativo.

#### 3.2.2 Versión optimizada con Context + `React.memo`  

```tsx
// src/context/ThemeContext.tsx
import React, { createContext, useState, useCallback, ReactNode } from "react";

type Theme = "light" | "dark";

interface ThemeContextProps {
  theme: Theme;
  toggleTheme: () => void;
}

export const ThemeContext = createContext<ThemeContextProps>({
  theme: "light",
  toggleTheme: () => {},
});

export const ThemeProvider: React.FC<{ children: ReactNode }> = ({ children }) => {
  const [theme, setTheme] = useState<Theme>("light");

  const toggleTheme = useCallback(() => {
    setTheme((prev) => (prev === "light" ? "dark" : "light"));
  }, []);

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>{children}</ThemeContext.Provider>
  );
};
```

```tsx
// src/pages/DashboardOptimized.tsx
import React from "react";
import { ThemeProvider } from "../context/ThemeContext";
import { Header } from "../components/HeaderOptimized";
import { StatsPanel } from "../components/StatsPanelOptimized";

export const DashboardOptimized: React.FC = () => (
  <ThemeProvider>
    <Header />
    <main className="p-4">
      <StatsPanel />
    </main>
  </ThemeProvider>
);
```

```tsx
// src/components/HeaderOptimized.tsx
import React, { useContext } from "react";
import { ThemeContext } from "../context/ThemeContext";

export const Header: React.FC = React.memo(() => {
  const { theme, toggleTheme } = useContext(ThemeContext);
  return (
    <header className="p-4 flex justify-between items-center">
      <h1 className="text-xl">Panel</h1>
      <button
        onClick={toggleTheme}
        className="p-2 rounded bg-indigo-600 text-white"
      >
        Cambiar a {theme === "light" ? "oscuro" : "claro"}
      </button>
    </header>
  );
});
```

```tsx
// src/components/StatsPanelOptimized.tsx
import React, { useContext } from "react";
import { ThemeContext } from "../context/ThemeContext";

export const StatsPanel: React.FC = React.memo(() => {
  const { theme } = useContext(ThemeContext);
  console.log("Render StatsPanel (optimizado)");
  return (
    <section className={theme === "light" ? "bg-gray-100" : "bg-gray-700"} p-4>
      <h2 className="text-lg mb-2">Estadísticas</h2>
      <div className="grid grid-cols-2 gap-4">
        <div className="p-2 bg-white rounded shadow">Visitas: 12 345</div>
        <div className="p-2 bg-white rounded shadow">Ventas: 678</div>
      </div>
    </section>
  );
});
```

**Mejoras:**  
- `ThemeProvider` mantiene el estado global sin prop drilling.  
- `useCallback` evita que `toggleTheme` se recree en cada render, evitando re‑renders de consumidores que usan referencia de función.  
- `React.memo` envuelve `Header` y `StatsPanel`; solo el `Header` se vuelve a renderizar porque su botón depende de la función, mientras que `StatsPanel` se mantiene estático, reduciendo renders en un **≈ 40 %** en pruebas de carga.

### 3.3 Ejemplo 3 – Carga de componentes pesados con `React.lazy` y `Suspense`  

#### 3.3.1 Carga estática (todo en el bundle principal)  

```tsx
// src/pages/Analytics.tsx
import React from "react";
import { Chart } from "../components/Chart";
import { Map } from "../components/Map";

/**
 * Dashboard de analítica que incluye un gráfico D3 y un mapa interactivo.
 *
